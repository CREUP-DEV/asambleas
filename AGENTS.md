# CREUP Assemblies - Agent Instructions

These instructions are the source of truth for agents editing this repository. [`docs/README.md`](docs/README.md) indexes the rest of the documentation. The domain model and the API live in [`docs/design.md`](docs/design.md), [`docs/api.md`](docs/api.md) and [`shared/types/api.ts`](shared/types/api.ts); [`docs/proceso-asambleas.md`](docs/proceso-asambleas.md) records how CREUP assemblies work today.

## Non-Negotiable Rules

- Follow these instructions before local preference or generic framework advice.
- Write code, identifiers and code comments in English.
- Put every user-visible UI string behind i18n keys in Spanish and English.
- Do not translate document or amendment content; users write that content directly.
- Keep Google authentication mandatory before any app access.
- Background work and persistent state use PostgreSQL, pg-boss or in-memory cache as described here. Local email goes to Mailpit (`docker-compose.yml`).
- Validate all untrusted input with Zod v4 from `zod/v4`.
- Protect every mutation with CSRF and same-origin checks.
- Store document content as structured blocks validated with `blocksSchema`; never store or echo raw HTML. Render it only through `shared/utils/content/render.ts`, which escapes everything. Formulas are the one markup it does not build itself: MathML that Temml makes from their LaTeX source (`shared/utils/content/formula.ts`), untrusted (no `\href`, `\url` or HTML macros, an unknown command shown as source) and checked tag by tag and attribute by attribute against a MathML allowlist (`isSafeMathMl`), else shown as its escaped source. A bare `http`/`https` address typed as text (footnotes and bibliographies imported from DOCX) is drawn as a link (`withAutolinks` in `shared/utils/content/autolink.ts`, called by `renderBlocks` and `renderAnnotated` over the text as it reads now): the sentence's closing `.`, `,`, `;`, `:`, `!`, `?`, `…`, `'` and a closing bracket the address did not open stay outside it, and it never goes inside a stored link, a formula or a formula block, nor over removed text in a diff. It is never stored: blocks, marks, diffs and the exports (PDF, DOCX) keep the text as typed (user's decision of 2026-11-21).
- Store amendments as operations anchored to the document's frozen base version. Never store modified copies of the text.
- Use optimistic locking on shared PUT/PATCH mutations.
- Run the verification checklist before finishing code changes.
- This repository is public. Anything that identifies the production server (user, paths, networks, what else runs there), describes an open security weakness of the platform or of the Intranet, or carries real people's data or real email addresses goes to `docs/private/` (local only, ignored by git and Docker; its `README.md` says what goes there), never to a tracked file or a commit message. Examples and tests use `example` domains. Working reports, audits and one-off plans go to `docs/private/` too.

## Project Overview

Internal platform for CREUP assembly management:

- assemblies and lifecycle state;
- recursive agenda items;
- platform documents and uploaded PDFs;
- amendments, transactional amendments and incorporation history;
- role synchronization from the CREUP intranet;
- async PDF exports with accessibility preferences.

The public website lives in a separate `creup/web` repository. This app may mirror visual identity and selected helpers, but it has its own database, auth scope and deployment model.

## Language, i18n And Accessibility

- UI text must use `t('key.path')` or another existing i18n-aware API.
- Add keys to both `i18n/locales/es.json` and `i18n/locales/en.json`.
- Run `pnpm i18n:check` and `pnpm i18n:audit-identical` after adding text.
- Admin pages, toasts, aria labels, button labels, validation copy, badges and error states count as UI.
- Visible text should not use long dashes or legacy assembly labels such as `Nº 80`; use shared formatters such as `80.ª AGO`.
- Content accessibility preferences apply only to document/amendment content, not UI chrome:
  - Raleway;
  - Atkinson Hyperlegible;
  - OpenDyslexic;
  - text alignment (user's decision of 2026-11-23): justified by default, or aligned to the left. On screen `.rich-text` is justified with `hyphens: auto` (headings, table cells, formulas and `cx-align-*` blocks set their own) unless `<html>` carries `content-ragged`; the PDFs follow it through `justified` in every export request (`ExportButton`, `usePackageDownload`), true when absent.
- Never put body text in a status colour (`success`, `info`, `warning`, `error`) on a tint of that colour: yellow text in a yellow box does not read, and the others are hard work too. Status boxes keep their text neutral (`text-default`, `text-highlighted`) and use the colour only on the icon, the border or the ring. `UAlert` does this for every status colour through `app/app.config.ts`, so never pass `:ui` classes that colour its title or description again; hand-built boxes (`bg-<colour>/5`, `bg-<colour>/10`) follow the same rule. Only a large result heading (an outcome, a count) may keep its colour. Light mode uses the 700 step for `--ui-success`, `--ui-info`, `--ui-warning` and `--ui-error` (`main.css`) so standalone status words and white text on a solid status background pass WCAG AA; status badges and buttons on a tint go one step darker (`app.config.ts`).
- Raleway, the UI font, is self-hosted (`app/assets/css/fonts.css`, from `server/assets/fonts`) with `ascent-override`/`descent-override` pinned (88%/29.4%: the hhea total, split so the box's middle falls between the middle of the lowercase letters and of the capitals). Without them Windows lays it out with `winAscent` (1154 of 1000) and every line of text sits 2 to 3 px below the icons next to it; with the plain hhea split (94%/23.4%) icons sat on the capitals' middle and looked high next to lowercase labels. Never move it back to a provider of `@nuxt/fonts`, which cannot set overrides. Align an icon with its text with `flex items-center` (or `self-center` in an `items-baseline` row), never with margin nudges tuned on one browser. A label of digits only next to a dot or an icon (the projection's clock) trims its text box to the capitals (`[text-box:trim-both_cap_alphabetic]`; the figures are lining) and sits in one `items-center` row with the dot sized in `em`, so the dot centres on the digits rather than between the lowercase and capital middles (user's decision of 2026-11-19); a browser without `text-box-trim` (Firefox) centres it on the line box as before. The icon's own wrapper must be flex too: an icon alone in a block element (a `<dt>` next to an `sr-only` label) sits on the text baseline and comes out 2 to 3 px high. An icon inside running text that wraps uses `align-middle`, which centres it on the lowercase letters; in an `items-start` row the icon takes `mt-*` of (line height minus icon size) / 2. Raleway ships no tabular figures (its features are ccmp, dnom, frac, liga, lnum, locl and numr; no `tnum`), so `tabular-nums` changes nothing with it and every lining digit has its own width (0.416em to 0.701em). A number that ticks where the text around it must not move (a turn's clock, the projection's live tally and recess countdown) goes through `CommonTabularDigits` (`app/components/common/-digits.ts`, `digitCells`), which puts each digit in a centred cell of one width (`TABULAR_DIGIT_EM`, 0.71em, the Bold zero) and keeps the text once for screen readers (user's decision of 2026-11-21); keep `tabular-nums` beside it for another font.
- Diff UI must support color mode and marks mode. Render diffs, provenance and plain text through the shared engine (`shared/utils/content/render.ts`) and `app/components/content/*`, never with component-level diff logic. Colour mode is soft (`--cx-*` in `main.css`): changed text keeps the colour of the text around it, added text sits on a pale green tint with a thin underline, removed text is dimmed and struck through on a pale red tint; the hue goes on the line and the tint, never on the text. Pass `focus` (the ring, `.cx-focus`) only where several amendments show together (provenance), never on a single amendment's diff. A diff numbers ordered items as the PDF does: an item an amendment deletes takes no number (`cx-uncounted`, the PDF's `countable`; one carrying `start` hands it on, `handedOnListStarts`), and `previewAmendment` fragments carry their real numbers (`fragmentListStarts`, `struckListNext`), so an amendment to "k)" reads "k)" and two runs apart never read as one list. An editor seeded with a passage keeps its numbers (`seedListStarts`) and passes the base blocks before it to `diffPassage` (`before`), so those starts are no change of format. The projection shows only the blocks an amendment changes (context 0), fits its text to the free height down to a readable floor, scrolls to the first change and always uses strong marks, whatever the diff mode; it never forces light mode. Rendered text never widens its column: `.rich-text` breaks a run that cannot fit its line (`overflow-wrap: break-word`, which leaves ordinary words whole and tables' columns as they are) and a link, the autolinked addresses included, breaks anywhere; every `fr` grid track of the projection is `minmax(0, …)` and its items `min-w-0`, so no content (17.13 of the 80.ª AGO, a footnote's 181-character address) pushes the page past the screen. Never hide such overflow with `overflow-x: hidden` on a root (user's decision of 2026-11-21).
- Single-letter shortcuts (no modifier) can be turned off per browser (WCAG 2.1.4): every handler reads `useSingleKeyShortcuts().enabled` (`app/composables/accessibility/useSingleKeyShortcuts.ts`, localStorage, on by default, restored once hydration ends) and does nothing when it is false. The switch is the same `USwitch` in `ShellPreferences` and in every shortcut help (`ProponentReviewShortcutHelp`, the console toolbar's popover). While it is off, no kbd hint, tooltip or `aria-keyshortcuts` names a letter. The Mesa console's keys also do nothing while a console dialog is open (every console modal keeps its open state in `useSessionConsole`) or the focus is in a dialog, popover or field (`shortcutKeyIgnoredAt`, `app/composables/session/shortcutGuards.ts`; never guard `[role="menu"]` there, the card menu announces the keys). Their target follows the debate (`focusedId` moves with `liveState.amendmentId`), and `a` or `l` on an amendment that is not in debate asks first, naming its code.
- Relative dates go through `formatRelative` (`app/utils/format.ts`): under 24 hours it truncates hours and minutes, so a countdown never claims more time than is left; from there on it counts calendar days in Europe/Madrid (`assemblyDayOffset` in `shared/utils/calendar.ts`), so a deadline at 23:59 tomorrow reads "mañana" however many hours are left. The deadline a page is about (`DocumentHeader`, `ProgressBanner`, the hub's next milestone, the agenda item reader) passes `dated` to `CommonCountdown` ("mañana a las 23:59", `datedCountdown`); lists of many dates do not. A past moment such as a headcount uses `formatMoment`, which adds the day when it is not today ("ayer, 18:45").

## Authentication And Role Sync

- First interaction is Google authentication.
- Unauthenticated users go to `/login`. The global middleware (`app/middleware/auth.global.ts`, decisions in `-session.ts`) sends to the login page of the page's language only when `GET /api/auth/session` answers 401 (or 403); a network error, a 429 or a 5xx lets the navigation through and keeps the last verdict, and a verified session is re-checked every 2 minutes, never when only the query or hash changes. `/login` sends an account already signed in to its `redirect` (`safeRedirectPath`: same-site paths only). Never bring back a redirect to `/login` on every fetch error.
- All authenticated Google users may sign in (there is no allowlist), except an account deleted in the Intranet. That is an authenticated lookup (token set) answering 404 with exactly `{"error":"not_found"}` for an account the Intranet knew before (`externalRole` or `intranetId` set). It revokes access in one transaction: `accessRevokedAt` and `accessRevokedReason` (`intranet_deleted`) together, role `Invitado`, member cleared, every session deleted, open impersonations of it closed (`revoked`), `user.access_revoked`, and the sign-in refused (the login page of the user's language with `?error=access_revoked`, sent as `errorCallbackURL`). Exceptions: a `PROTECTED_ROLES` account keeps everything and gets `user.intranet_missing`; a Google account the Intranet never knew stays as before. Any other 404, a timeout or a 5xx is a plain failure and changes nothing.
- A revoked account gets access back only at a sign-in whose authenticated lookup returns it (`user.access_restored`, then normal role sync). Never restore it by hand: the Intranet is the source of truth. Its role never changes by hand (409 `admin.users.errors.targetRevoked`), and an Admin without access does not count as the last Admin.
- Sessions last 7 days and renew at most once a day while the app is used, so sign-in alone misses an account that keeps its session. Only the browser renews them: `app/plugins/session-keepalive.client.ts` asks better-auth's `GET /api/auth/get-session` with `disableCookieCache` about every 3.5-4 minutes while a page is visible (a little after ready, shown again, back online, and a 20 s check; every tab shares the time; random waits keep a venue under better-auth's 100 per 10 s per IP), which extends the row and the cookie together once a day and re-sends the 5-minute `session_data` cookie cache, so most requests skip the session read (`refreshCache` cannot do it: better-auth turns it off with a database); `requireAuth` reads the session with `disableRefresh`, since a refresh there sends a `Set-Cookie` that never reaches the browser. Never enable `deferSessionRefresh`, and never read that answer as the identity (`/api/me`). The daily access re-check (`recheckIntranetAccess` in `server/utils/auth/accessRecheck.ts`, pg-boss queue `users-access-recheck` at 05:30 Europe/Madrid) looks up every account with a live session, access, intranet data and no protected role, one every 500 ms, and calls `applyIntranetNotFound` on each authenticated `notFound`; it never runs role sync. More than max(3, 30%) not found of the accounts the Intranet answered for revokes nobody and records `users.access_recheck_blocked`.
- `getAuthUserWithRole` reads `access_revoked_at` on every request and answers 401 for an account without access, so better-auth's 5-minute session cookie cache never keeps a revoked account in. Never add `accessRevokedAt` to `AuthUserWithRole`.
- Before the session is created (`databaseHooks.session.create.before`, `checkSignInAccess` in `server/utils/auth/roleSync.ts`), look the account up once with `lookupIntranetRole` (`server/utils/members/intranet.ts`): `POST` `{ "email": "user@creup.example" }` to `getRoleApiUrl()` with `Accept: application/json`. Role sync in `session.create.after` reuses that answer. Every intranet call (role sync and roster sync) sends `Authorization: Bearer <NUXT_INTRANET_API_TOKEN>` when the token is set (`intranetAuthHeaders`).
- Always update `externalRole`, `externalName`, `externalInitials`, `university`, `universityAcronym` and `lastRoleSyncAt` when the lookup succeeds, and `intranetId` when the answer carries an `id`. A failed lookup writes nothing, `lastRoleSyncAt` included.
- Avatars without a photo read `avatarText` (`MeDto`, `AdminUserDto`, `StatsAccountDto`), worked out on the server by `accountAvatarText` (`shared/utils/accountAvatar.ts`): the acronym of the member an account acts for when it is not a council (`ANEM`, `SE`, `CAS`), otherwise the university's acronym (`users.university_acronym` from the role lookup, else `members.university_acronym` from the roster), else the council's acronym. A university acronym comes only from the Intranet (`university_acronym`, the last word of the council's Google name): never derive it from the university's name (UV is València, so Valladolid is UVa). Case is kept. `AccountAvatar` and the user menu draw it through `avatarDisplayText` and `avatarTextClass` (`app/utils/accountAvatar.ts`): up to four letters, the type shrinking with the length to fit the circle; a longer one gives way to the initials of the name.
- Photos are stored here, never loaded from Google (user's decision of 2026-11-16): `users.image` keeps the Google URL better-auth wrote and no DTO sends it. `MeDto.image`, `AdminUserDto.image` and `StatsAccountDto.image` (and `AuthUserWithRole.image`) are the stored photo's URL, `avatarUrl` of `user_avatars.file`, or null (`server/utils/auth/avatarFiles.ts`). The pg-boss queue `user-avatars` (`server/utils/auth/avatars.ts`, on the export queue's instance) fetches `lh3.googleusercontent.com` only (`isAllowedAvatarSource`: https, no redirect followed, 10 s, 5 MB), draws a 192 × 192 WebP with `renderSeatingImage` under `UPLOAD_STORAGE_DIR/avatars/<userId>-<version>.webp` (version: a hash of the source) and names it only while `users.image` is still that URL and the account has access, under the account's row FOR SHARE. `decideAvatar` is the one rule (fetch, drop, none): a source already fetched is never fetched again, file or not. Jobs come after a sign-in (`refreshUserAvatar`, never awaited) and once per boot (`backfillUserAvatars`); `applyIntranetNotFound` deletes the row with the access and the file after commit. `GET /api/uploads/avatars/[file]` serves only a file a row names now, to signed-in accounts. Logs carry the user id, never the URL, and errors only by name and SQLSTATE (`seatingErrorSummary`: the claim's query binds the URL).
- If the Intranet lookup fails, log a warning and do not block sign-in. A database error in the access check refuses it (`sign_in_unavailable`) rather than let a deleted account in. Logs carry `accountRef` (`emailFingerprint`), never the email.
- `INITIAL_ADMIN_EMAIL` receives `Admin` on first sign-in.

## RBAC

System roles:

- `Admin`
- `Secretaria`
- `Presidencia`
- `Moderador`
- `CEA`
- `Asociado`
- `Sectorial`
- `CAS`: the Coordinación del CAS (Comité de Asuntos Sectoriales). In the Intranet a CEA account, the responsible of the committee whose acronym is `CAS` in its committee management; the role lookup answers `CAS` for it, and here it presents for the member `CAS` (kind `other`, from `/usuarios/cas`), never as an office of the CEA. The Secretaría del CAS is of type `Otros` there: it gets `Invitado` here by hand.
- `CAI` and `CdG`: the members of the Comité de Asuntos Internacionales and the Comité de Garantías (intranet types `CAI` and `CdG`; the Coordinación del CAI is a CEA office). They read like `Invitado`, and the Mesa marks them at the headcounts as guests (`HEADCOUNT_GUEST_ROLES`).
- `Invitado`: given here by hand by whoever manages roles, never by role sync. It reads like `Otro`, and the Mesa marks its accounts at the headcounts, as guests without a vote.
- `Otro`: every other account (any other intranet type, or none). It reads what is published and appears nowhere else.

`isReadOnlyRole` (`shared/constants/roles.ts`) is true for both, and for `CAI` and `CdG`. Audit rows written before the rename that say `Invitado` meant today's `Otro`.

`Admin` bypasses all permission checks through the RBAC helper. Do not reimplement ad hoc admin bypasses. `Admin`, `Secretaria`, `Presidencia` and `Moderador` are `PROTECTED_ROLES`: role sync never changes them. The association's Secretaría and Presidencia hold every permission, users and roles included; the Mesa (Vocalía and Presidencia de la Mesa) uses `Moderador`. Only an Admin gives or takes the `Admin` role or touches its permissions. Only an Admin changes the access of Secretaría and Presidencia: giving or taking either role, what either grants, and the grants of an account holding either (`touchesLeadershipRole`), so neither changes the other's.

### Members

- Documents and amendments are presented by members (`members`): student councils (asociados), sectorials and executive offices. The executive offices are the single-person offices, "cargos unipersonales", of the Comisión Ejecutiva Ampliada such as PRES or SE, whose kind is labelled just "CEA" (sentences about one office still say "cargo de la CEA"), and never called areas in visible text; code identifiers keep `executive`; the `CEA` role is shown as "Comisión Ejecutiva Ampliada (CEA)", and the UI and PDFs never say "Comisión Ejecutiva" alone.
- Asociados, sectorials, the CEA's offices and the CAS are synced from the intranet roster (`/usuarios/asociados`, `/usuarios/sectoriales`, `/usuarios/cea`, one account per office, which outlives whoever holds it, and `/usuarios/cas`, the Coordinación del CAS as the member `CAS`, kind `other`, under the committee's name), by hand and daily at 05:00 Europe/Madrid (pg-boss, `server/utils/members/schedule.ts`), all the same way: matched by their Intranet id (`members.intranetId`, unique when set) first, so an acronym change updates the member, then by the account's email (`members.email`, unique when set), so an account recreated with a new id keeps its member, and deactivated once the Intranet no longer lists them. The acronym (the intranet's `initials`) only matches a member that stores no other id or email (members from before, manual offices): it never hands a member to another account, and a new account whose acronym another member keeps is not created (`acronymConflicts`). `members.email` never reaches a client, an audit row (`memberAuditState`) or a log. The Secretaría can assign documents to an office before anyone signs in.
- What the Intranet lists and a sync cannot store (an acronym listed twice, or already held by another member, and accounts without initials) is never dropped in silence: `MemberSyncResult.ignored` carries it, the members page warns, and the `members.sync` audit row keeps it (the daily run has no screen).
- Offices used to be manual members: a manual `executive` member whose acronym the CEA list names is adopted (`adopt` in `planRosterSync`, `server/utils/members/roster.ts`) and syncs from then on; one the list does not name stays manual, and no sync touches it. Every other manual member is never touched. The CEA and CAS lists are optional (`OPTIONAL_ROSTER_KINDS`): when the Intranet cannot give one, the sync goes on, leaves those members as they were (none created, updated nor deactivated) and says so in `MemberSyncResult.skipped`. The CAS list adopts a manual `other` member `CAS` the same way; the other manual `other` members (say the CAI or the CdG as presenters) are never touched. The CAS was a CEA office before: matched by its Intranet id, that office becomes the member `CAS`.
- A roster sync that would deactivate every active asociado, sectorial or office, or more than max(3, 30%) of them, is not applied unless the body says `confirmDeactivation: true` with `confirmedKinds` covering what it would deactivate now (`isDeactivationConfirmed`): otherwise it records `members.sync_blocked` and answers 409 `large_deactivation` with the current counts. The daily run never confirms, and its audit rows have actor null.
- Every list of members follows one order, `orderMembers` (`shared/utils/memberOrder.ts`): asociados, sectorials, the others and the CEA's offices, each by acronym, inactive ones last. The headcount is the one exception (`compareRollCall`, see the headcounts under Amendments). `GET /api/members` answers in it. Menus that pick members (who presents a document, the authors of an amendment or a transactional, the delegations of a headcount, who asks for the floor) show the acronym and, below it, the whole denomination and university, never cut (`memberMenuItem`, `MEMBER_MENU_UI` in `app/utils/format.ts`). Wherever a member is named by its denomination (a menu, a tooltip, a hover card, a list in a popover), a council's goes with its university (`memberDescription`, "Consejo de Estudiantes · Universidad de Córdoba"; the university comes from `MemberDto.university`, never on a `MemberRef`), since councils share the same or nearly the same denomination (user's decision of 2026-11-17), and a long name wraps, never cut. Every acronym opens the member's card on hover (`CommonMemberBadge` over `CommonMemberCard`, the members read once per page through `useMemberDirectory`; never on the projection, which passes `tooltip: false`), and a badge that shows the name adds a council's university. The generic "CEA" (`GENERIC_EXECUTIVE_MEMBER_ID`) shows the CREUP imagotype, the emblem over the word "CREUP", as its card's avatar (`/marca/imagotipo-granate.svg`, square on the beige of `isotipo-granate.svg`; user's decisions of 2026-11-19). A card that sets a name in bold (`CommonMemberCard`, also the sheet's «+N» lists) puts a council's university in bold and its kind and denomination under it, so the bold line tells councils apart. Its avatar is `MemberDto.image`, the stored photo of an account that acts for the member (`memberImages` in `server/utils/members/images.ts`: a council's or a sectorial's logo), only in `GET /api/members`; an office's only to those who see the offices, never with `?for=amendment` (it may be its holder's). Where someone chooses who presents a document or an amendment, its own kind goes first (`orderMembers(list, member.kind)` in `AmendmentComposer`, `AgendaNewDocumentModal`, `AgendaBulkDocumentsModal` and `DocumentMetadataForm`); only the order changes, never who is listed.
- Who holds each CEA office comes with the CEA list (`holder_name`: the name and surnames in the holder's Intranet profile, docs/intranet.md) and is stored in `members.holder_name` (`MemberDto.holderName`). It is personal data: it reaches only those who see the offices (`GET /api/members` collapses the offices for everyone else and sends it null with `?for=amendment`), never an audit row (`memberAuditState`) nor a log. The control sheet's presenter card shows it next to "CEA".
- `users.memberId` links an account to the member it acts for. In the intranet an Asociado or Sectorial account is the member itself, a CEA account is its office's place, and the Coordinación del CAS (role lookup `CAS`) is the member `CAS` (`canLinkToMember`: only an `other` member). All four link by `users.intranetId` = `members.intranetId` first, then by `users.email` = `members.email`, then by initials, never to a member that stores another account's id or email (`server/utils/members/link.ts`); a member created at a sign-in is an intranet member with that id and email (an office or the CAS named after its acronym until the next sync, since the account carries its holder's name). Whoever holds `user:manage_roles` can link any account by hand (`PUT /api/admin/users/[id]/member`), and a CEA account keeps such a link while its initials stay the same.
- Who sees the executive offices is one predicate, `canSeeExecutiveMembers` (`server/utils/domain/visibility.ts`): the roles Admin, Secretaría, Presidencia, Moderador and CEA, the holders of `document:manage`, `amendment:review`, `amendment:manage`, `assembly:manage`, `session:moderate`, `member:manage`, `user:manage_roles`, `stats:view`, `notification:manage`, `control_sheet:view`, `control_sheet:edit`, `session:record_speakers`, `seating:view` or `seating:edit`, and an account that acts for an office (`Actor.memberKind`). Everyone else gets from the server one generic presenter, `GENERIC_EXECUTIVE_MEMBER` (`CEA`, "Comisión Ejecutiva Ampliada"), instead of any office; never hide an office on screen instead.
  - Every answer that carries a member goes through the helpers there: `redactMember`, `redactMembers`, `redactPresenters`, `redactAuthors` (remaps `mainAuthorId`), `redactAcceptances`, `redactEventActor` (also drops the name of the person who acted for an office), `redactPayloadMembers` with `loadExecutiveMask` (member ids in payloads), `collapseExecutive` (`GET /api/members`) and `visibleAcronym` (PDFs, every one of them built with the requester's actor, the annotated PDF and the assembly dossier included; which amendments an annotated PDF carries is the one thing decided as a public reader, `publicExportActor` in `server/utils/export/actor.ts`: only published ones, whoever asks; the documentation package is the one export built wholly as that reader, since one ZIP goes to everyone). `MeDto.member` stays real. A new DTO with a `MemberRef` or a member id uses them.
  - `GENERIC_EXECUTIVE_MEMBER_ID` is never a member. On a document, an account that does not see the offices neither adds nor removes one: bodies go through `resolveBodyMembers` (`server/utils/domain/executiveMembers.ts`), which answers 422 `executive_member` for an office by its real id (there or not) and for the generic id with no office there, and keeps the offices that are.
  - Amendments and transactionals are the one exception: the CEA presents them too, and any member may present one with it. Only in the composer are the real offices read by accounts that do not see them. An account that presents amendments for a member (`canNameExecutiveAuthors`) reads the list to pick from, `GET /api/members?for=amendment` (`AMENDMENT_AUTHORS_QUERY`; nothing but the two composers may use it). Whoever may edit a draft reads its real authors and main author, `GET .../amendments/[amendment]/authors` (`amendmentComposerAuthors`, `AmendmentComposerAuthorsDto`): exactly the checks of `updateAmendmentDraft`, so an author (`composerAuthorsAccess`) of a draft, one sent back for correction included, while the document still takes amendments (`assertAmendable`: 409 once it is voted or the assembly closed). Both carry members only, never who acts for them. So while it composes, whoever may edit a draft always sees which offices present it and which is the main author, and names every office by its real id. Those bodies go through `requireAmendmentBodyMembers`: the generic id is never an author (422 `executive_author`, for everyone), an office named as main author follows the rule of any member (it must be among the authors the body ends with), and an account that neither sees nor may name the offices cannot name one (422 `executive_member`), except to keep the ones already on the draft it edits (`known`, passed only by `updateAmendmentDraft` after its edit checks: that account reads them in the composer). Everything those accounts read outside the composer, its own draft included (lists, the detail, history, news, activity, PDFs), is the generic "CEA".
  - That account knows every real office id, so outside those two reads no answer may tell which offices an entity has: on a document never accept a real id "because it is already there" nor count the offices behind the generic entry in an error, and on an amendment check that the actor may edit the draft (author, draft, `assertAmendable`) before any answer that depends on its authors. `redactPayloadMembers` puts the generic id last in every list of ids, since stored lists are sorted by id.
  - On the client the generic entry is told by its id, never by the viewer's role (`app/utils/executiveMembers.ts`): a picker that adds members passes its list through `addableMembers`, a generic entry already on a document is shown fixed (`withFixedGenericExecutive`), a draft whose authors carry it gets its real authors before its composer opens (`hidesExecutiveAuthors`, `loadDraftAuthors` in the document page; the composer never offers nor sends the generic entry), and filters by member use it as any other id. The 422 is worded once, in `useApi().notifyError` (`errorReasonKey`). `MeDto.seesExecutiveMembers` (`useMe().seesExecutiveMembers`) only words hints (outside the composer the offices a member names read as "CEA"); never use it to hide or show data.
  - The projection is opened on a Mesa account but read by the room: every read it makes sends `?view=room` (`ROOM_VIEW_QUERY`, `shared/constants/roomView.ts`) and each endpoint it reads calls `requireViewer` (`server/utils/domain/roomView.ts`) first. The flag is honoured only for `session:moderate` (403 otherwise) and only on GET; with it the request answers as `roomViewer`, an account that sees only what is public, so every visibility rule and `redact*` applies by itself (offices read as "CEA", nobody speaking for one is named, nothing unpublished goes out). A new endpoint the projection reads calls `requireViewer`, or it shows the room the Mesa's view. Never hide offices on the projection's client instead.
  - Amendments whose main author is an office are coded `CEA1`, `CEA2`... for everyone, numbered per document across all the offices (`amendmentCodePrefix`): a code never names the office.

### Assemblies

- Status: `draft -> convened -> in_session -> closed` (see `ASSEMBLY_STATUS_TRANSITIONS`).
  - `draft` is visible only to managers.
  - Nothing is projected or recorded in the room until the Mesa opens the session (user's decision of 2026-11-18): pointing the live state at an item, a document, an amendment or a vote, the Mesa's outcomes (all but `reopen`), final votes, votes on an agenda item, headcounts and speaking turns answer 409 (`assertSessionOpen` in `server/utils/domain/sessionOpen.ts`, `data.messageKey` `common.errors.sessionNotOpen`) unless the assembly is `in_session` (`isSessionInProgress` in `shared/utils/sessionGate.ts`); the Mesa's outcomes, votes between alternatives, final votes and votes on an agenda item check it again on the status read under the assembly's share lock (`shareLockAssembly`; `lockOpenSession` for amendments), which a status change waits for, so none lands after a suspension. "Suspender sesión" goes back to `convened`: then only what clears the room goes through (`liveStateClearsOnly`: clearing the debate, hiding the speaking turns, the message; `speakerUpdateClearsOnly`: ending the floor or taking a turn off the list), so a break never leaves something on screen or someone speaking. Corrections of the record (`reopen`, annulling a final vote, voiding an item vote, unanimity) wait only for the assembly to be open. The console mirrors it through `useSessionConsole().inSession` (buttons disabled) and `requireInSession` (what a menu, a shortcut or an open dialog would still send); never a check per component of the status.
  - The agenda turns final (ODD definitivo) on its own when the calendar's `agenda_final` date comes: `agendaFinalSince` (`shared/utils/calendar.ts`) gives `AssemblyDto.agendaFinalizedAt` and the server's `isAgendaFinal`. Nobody marks or reopens it by hand; moving that date moves it, and without it the agenda stays provisional. Only a provisional agenda shows a badge ("provisional"); a final one shows none. The column `assemblies.agenda_finalized_at` and the events `agenda_finalized` and `agenda_reopened` are from before. Nothing is locked then: creating, renaming, moving or deleting a root item needs `confirmFinal: true` in the request (409 with `data.code` `agenda_final` without it, so the client asks and retries) and its event carries `afterFinal: true`. Every such path goes through `confirmFinalRootChange` (`server/utils/domain/assemblies.ts`). Sub-items never need it.
- Each type keeps its own counter: `(type, number)` is unique.
- Calendar milestones live in `assembly_milestones`, seeded by `defaultMilestones` and checked by `checkCalendar`, both from the calendar rules of the type (`calendar_rules`: default offsets, regulatory minimums, documents sent with a short convocation, reform window; read from the 2025 RRI and RFAG, since the 2026 drafts were never approved). The rules are data, edited at `/admin/calendario` (`CALENDAR_RULES_PERMISSION`); never hardcode a regulatory deadline. `INITIAL_CALENDAR_RULES` is only what `pnpm db:seed` stores for a type with no row (it never overwrites one).
- Per-assembly policies live in `assemblies.settings`. Always read them merged over `DEFAULT_ASSEMBLY_SETTINGS`.
- Public routes use readable slugs (`80-ago`). Resolve them server-side with `server/utils/domain/resolvers.ts`.

### Agenda Items

- Recursive tree through `parentId`. Load the rows flat and build the tree client-side.
- Reorder operations must validate parent existence, assembly ownership and cycles.
- Every transaction that writes agenda rows takes `lockAssembly` first (`server/utils/domain/agendaWrites.ts`): the agenda endpoints, and the document paths that create, rename or remove an automatic sub-item (creating a document, deleting one, and `updateDocument` when it moves or renames one). Lock order: assembly, then documents.
- An item where members present (a container) has `acceptsSubmissions` and `submissionKinds`, the document kinds it takes; empty means every kind (`itemAcceptsKind` in `shared/utils/agendaSubmissions.ts`). The kinds bind members, never managers (422 `submission_kind`).
- «Se vota el punto» (`agenda_items.voted`, `AgendaItemDto.voted`) marks an item voted by itself (a ratification, an election) rather than through its documents' final votes. Optional in bodies (a PUT that leaves it out keeps it), never refused, never `confirmFinal`, never stored on a container (`normalizeItemVoted` in `shared/utils/agendaSubmissions.ts`), and meaningless while a document of the item is voted (`itemHasVotedDocuments` in `shared/utils/controlSheet.ts`). It only lists the item in the control sheet and reads it «Pendiente» instead of «No aplica» until its vote; recording a vote on the item never needs it. Only managers see it (the item form, organize mode), never the convocation, PDFs or projection.
- A document created under a container, or moved to one, gets its own automatic sub-item in the same transaction (`insertAutoItem`, `bindAutoItem`; `agenda_items.generatedForDocumentId`), whoever creates it. Its title follows the document's until a manager renames it (`titleCustom`, `syncAutoItemTitle`), and it goes when the document is deleted or moved away unless it holds something else (`findRemovableAutoItem`, `removeAutoItem`); kept that way after a move, it stops being the document's and becomes an ordinary item that remembers the document in `hiddenWithDocumentId` (`unbindAutoItem`) until the document is deleted or a manager gives the item a new title; one a manager had already renamed (`titleCustom`) carries the manager's title and keeps no link (`keepsDocumentTitle`). Nobody, managers included, puts a document in another document's automatic sub-item (422 `auto_item`, `requireNotOthersAutoItem`), and the pickers leave those out. It never needs `confirmFinal` nor gets `afterFinal`. Its events carry `auto: true` and `documentId`.
- An automatic sub-item carries the title of its document, and so may one kept after its document moved away (`titleDocumentId` in `shared/utils/agendaSubmissions.ts`: `generatedForDocumentId`, else `hiddenWithDocumentId`). Never return that title to a viewer who cannot see the document, until it is published: agenda readers go through `visibleAgendaItems`, which leaves the item out, and send one that stays because of what it holds without its title (`hiddenTitleItemIds`; `AgendaItemDto.titleHidden`, worded by `agendaWithTitles` over the fetched agenda, and by `agendaHiddenTitle` in PDFs). Its events carry the `documentId` (`titleDocumentPayload`), and the activity shows them with the document's visibility; once that document is deleted, to everyone if it was public by then (`DeletedInfo.wasPublic`). Deleting a document that was never public leaves its title withheld on the items that carried it and stay (`withholdItemTitles` in `removeDocument`, `agenda_items.titleWithheld`; never one with `titleCustom`): only document managers read their title and description, and their events, until one of them gives the item a new title (PUT `[item]` clears `hiddenWithDocumentId` and `titleWithheld`). A masked item is sent without title, description and `generatedForDocumentId` (`toAgendaItemDto`), by the mutations too: an `assembly:manage` holder who may not read the title (`canReadItemTitle`) changes neither it nor the description. The neutral label is worded when read, never stored in fetched data (`agendaWithTitles`).
- Agenda numbers ("17.1") are never stored, and everyone reads the same number for the same item: the one an account that sees only what is public reads. `AgendaItemDto.unlisted` marks the items such an account does not receive (`unlistedAgendaItemIds` in `shared/utils/agendaNumbering.ts`, which asks `visibleAgendaItems` for that viewer; never a second copy of the rule), and `numberAgendaItems` there is the only numbering: it counts siblings skipping the unlisted ones, which get no number (null, nor anything under them), keep their place and never shift the others. `buildAgendaTree`, the session rows and the exports (`server/utils/export/mapping.ts`) all call it; never number by position anywhere else. Where a number shows, an unlisted item shows the neutral mark "Sin publicar" (`AgendaItemNumber`), and in sentences and labels `numberedAgendaTitle` or `agendaNumberInText` (`app/utils/agendaTree.ts`), so no label reads an empty number. The convocation leaves unlisted items out, and so does the projection (`proyeccion/[assembly].vue`, which reads everything in the room view), except the item the Mesa itself puts on screen: the room view's agenda adds it, still unlisted so no number moves, with its title only when the Mesa account reads it (`roomAgenda`, `withScreenItem` in `server/utils/domain/roomView.ts`), never a withheld title.
- Deleting an item removes its sub-items and every document under them (`removeDocument` for each, one `agenda_item_deleted` per item). Amendments keep it: any amendment row of any status under it answers 409 `agenda_item_amendments`. So do the control sheet's notes and a vote on one of the items themselves, voided too (409 `agenda_item_sheet`, `sheetNotesIn`). During the session, 409 `agenda_item_live` while the projection or an open speaking turn is on one of them.

### Documents

- Formulas (user's decision of 2026-11-20): a `formula` block (a displayed formula) and a `formula` mark (one inside a sentence) keep their LaTeX source as text, so amendments, diffs, the automatic merge and the Mesa's wordings treat them as any text. A formula block has no marks and no format (`blockFormatOf` is null, as for an image); a formula mark overlaps no other mark (`blocksSchema` splits the others around it). They are drawn as MathML on screen (`renderFormula`), as SVG by MathJax in PDFs (`server/utils/export/formulaSvg.ts`, base and AMS macros only; inline ones as text with real subscripts, `formulaRuns`) and as native Word equations on export (`formulaToDocx`, from Temml's MathML), text when a source does not parse. A diff shows a changed formula block's source with its changes marked and the formula drawn before and after; a formula a diff segment cuts shows its source. The editor edits the source as plain text (`FormulaBlockExtension`, `FormulaExtension`, `code` so no typing rule touches it) with the formula drawn below, and the toolbar's «Fórmula» inserts one. The DOCX import reads Word equations (Office Math): the converter replaces each `m:oMath`/`m:oMathPara` by a marker carrying its tree (`MATH_SCRIPT` in docx.ts), the server checks it and writes LaTeX (`server/utils/content/omml.ts`), a block when alone in its paragraph, a mark otherwise; one that cannot be read is left out with the warning `formulas_dropped`.

- `format`:
  - `structured`: blocks, amendable when `amendable`;
  - `file`: an uploaded PDF, never amendable.
  - Presenters and managers may switch it until publication (`DocumentFormatSwitch`); the draft text and the PDF both stay for a switch back.
  - A kind that takes amendments by default is presented as text: only managers create one as a PDF or switch one to it. The server refuses a non-manager with 422 `file_kind` (`fileFormatRefused` in `shared/utils/documentFormat.ts`), and the forms offer members no PDF there.
- Kind defaults (amendable, voted, majority, accepted amendments) come from `DOCUMENT_KIND_DEFAULTS`. An amendment vote proposes `amendmentVoteMajority` (absolute in a reform of the Estatutos or a regulation, simple otherwise). `acceptedAmendments` is per document: `incorporate` (regulations and the Estatutos, RRI art. 65.5) approves an amendment the main presenter accepts at once (approval method `proponent`), and changing that answer before the final vote reopens it; `vote` leaves it to the assembly. Only managers change it, never after the final vote, and the change applies to the amendments already answered (`applyAcceptedAmendmentsRule`). Where accepting would incorporate an undecided amendment, the presenter's review and the answer form (`AmendmentStep`, `PositionPanel`) say in quiet lines what it sets off: the overlapping amendments already approved it clashes with, the pending transactionals it withdraws (back if the answer changes before the final vote), and that everyone sees the approval while the answers are still reserved (`acceptIncorporates`, `incorporatedClashIds`, `answersReserved` in `app/components/proponent-review/-review.ts`).
- A document is always presented by someone: every create names a presenter (a manager's own member by default) and no update clears it (422 `presenter_required` in `planPresenters`); the forms offer no "nobody". Documents stored without one, from before, keep none until someone is named.
- A document has a main presenter (`proponentMemberId`), its proponent, and may have co-presenters (`document_proponents`, see `server/utils/domain/presenters.ts`). Co-presenters see and edit the draft like the main one and answer its amendments and transactionals like it (`isDocumentPresenter`: `can.position`, `setAmendmentPosition`, the review page `revisar`, proposing a transactional), but only the main presenter or a manager changes who the main presenter is (403 `main_only`); with co-presenters a main presenter is required. An answer records the presenter it was given for (`position_changed`'s `memberId`, `PositionDto.answeredBy`, masked for offices the reader does not see), so the others read who answered and get it in their news. Visibility checks take both (`DocumentPresenters`): load the co-presenters with the row (`resolveDocument`, `withCoProponentIds`).
- Who may present a kind is a rule of the member, not of the role: a sectorial or an `other` member (the CAS) never presents an internal motion, as main presenter or co-presenter, though it may amend one (`memberMayPresent` in `shared/utils/presenterKinds.ts`). The server checks the kind and every presenter a create or update ends with, for managers too (422 `presenter_kind`, `requirePresentersMayPresent`), and the forms leave those out.
- The presenters edit the working draft. Publishing freezes it as the immutable `base` version, and amendments anchor to that.
- Several people edit a draft by turns: saving checks the `contentHash` the editor started from (409 and a recovery panel when someone saved first), and a live event makes the other open editors load the new text or warn. The draft editor says who else has it open and who holds unsaved changes (`DocumentPresenceNotice`, `useDocumentPresence`, `POST .../presence`): a heartbeat kept only in this process's memory (`server/utils/live/presence.ts`, one app container), keyed by account and tab (a council's account is shared), never recorded and never sent over the live stream. Names go through `redactEventActor`; an impersonating Admin is never announced.
- The final vote stores the `consolidated` version produced by `consolidate`.
- PDF uploads must validate size, MIME and magic bytes.
- Every PDF of a document has a `document_files` row (`attachDocumentFile`). One replaced before publication goes with its row; one replaced once published stays on disk with `replacedAt` set, since delegates may have read it. Only document managers read those (`DocumentFileVersions` in the edit page, `GET .../files`, and the uploads route, which answers 404 to everyone else), and `removeDocument` removes them all with the document.
- An uploaded PDF shows its pages drawn by the platform with pdf.js on every screen, phones included (`DocumentPdfViewer` over `DocumentPdfPages`, in the document page, the consolidated text and the agenda item reader; user's decision of 2026-11-19), with the way to open it in a new tab to zoom, print or save it. The pages scroll with the page, so the read mark after them comes once the PDF has been scrolled through. Each page is drawn near the view and its pixels freed far from it (a drawn page weighs some 18 MB); its text layer (pdf.js `TextLayer`, transparent) lets its text be selected, found with the browser's search and read by screen readers, and its links to the web (`http:`, `https:`, `mailto:` only) open in a new tab. The session's preview and the projection leave the text and the links out (`:text-layer="false"`). The signed convocatoria of an assembly shows the same way on its convocatoria page (`assemblies.convocationFileUrl`, `/api/uploads/convocations/[filename]`, `server/utils/domain/convocation.ts`). That page is a section of the hub like any other (`convocatoria/index.vue`); only the generated convocatoria (`ConvocationSheet`) has a view outside the shell, to print it (`convocatoria/imprimir.vue`). Never bring back an `<iframe>` for a PDF. The tab keeps the PDFs it has read, with every page's size (`app/components/document/-pdfCache.ts`, the last two nobody shows; a stored PDF's url never names other content, since each upload gets a new name), so closing Directo's document window or leaving a page and coming back draws the pages without reading the file again. - Whoever manages documents (`document:manage`) edits a document's record (`DocumentMetadataForm`: title, kind, presenters, rules, deadlines) from its row of the documents page, and of the agenda in organize mode (`AgendaTreeContext.editRecord`), «Editar la ficha», in a side panel (`DocumentRecordDialog`, user's decision of 2026-11-21) that reads the whole document when it opens, closes once saved and makes the list read itself again; with unsaved changes only its own button closes it. `AgendaDocumentRow` takes those buttons in its `actions` slot.

- The acta de acuerdos is the one document the platform writes (user's decisions of 2026-11-21; `documents.generated = 'agreements_record'`, one per assembly, docs/api.md "Agreements record"). The Secretaría creates it from its section («Acta de acuerdos») under the item where it is read; it is published at once, voted and never amendable, and `regenerateAgreementsRecord` (`server/utils/domain/agreementsRecord.ts`, after a quiet spell, `server/plugins/agreements-record.ts`) replaces its base whenever the votes or the corrections change what it says: the one exception to an immutable published base, safe because nothing anchors to it. Its wording is `shared/utils/agreementsRecord.ts` only, from the control sheet's results, with the 79.ª AGO's format (numbered over the items with a result, «, por asentimiento» or «, por unanimidad» and nothing for a counted majority, resolutions, motions and executive reports lettered under one agreement, previous minutes in one sentence, «No se aprueba(n)…» for a rejection, elections naming the candidacy elected, no counts, no DNI). Its PDF carries the association's full name down the band (taller when the label needs it, `bandSvg`) and no «Aprobado en…» line, and keeps its closing formula, the signature, the name and the office in one unbreakable stack (`agreementsRecordBody` in `pdfBuilder.ts`, `RECORD_CLOSING_BLOCK_IDS`). Once approved (user's decisions of 2026-11-23, `server/utils/domain/agreementsSigning.ts`, docs/api.md «Regenerating and signing it»): corrections stay open and «Regenerar» writes it again as a consolidated version replacing the one in force (`regenerateApprovedRecord`), never by itself; the Secretaría prepares the PDF to sign, with the Secretaría Ejecutiva's visible signature read from the Intranet then (`GET firma-secretaria`) and never stored apart from that PDF (it is that person's data, deleted in the Intranet with the rest of it), signs it with AutoFirma (`public/autofirma`, `alwaysCreateRevision`) or outside and uploads it (a PDF with a signature dictionary); the signed PDF (`agreement_record_signings`, `DocumentDto.signedFile`) leads the document and stands for the generated PDF in the package, only while it signs the text in force. A regeneration takes it away.
- A document is expected (`isExpectedDocument`) when it has a `dueAt` or hangs from an item that takes no submissions and is not an automatic sub-item. A member's document in an automatic sub-item is never expected for that reason, so `documents_close` binds it.

### Amendments

- Operations: `replace`, `insert` and `delete`, anchored to base block ids. Validate them with `validateOps`. Every amendment has at least one.
- A `replace` also amends formatting (`shared/utils/content/format.ts`): optional `marks` (the inline formatting of its new text; with `text` equal to `baseText`, formatting alone) and optional `block` (the new format of the whole block: type, level, list, marker, start, alignment; alone on an empty operation at 0). Operations stored without them stay valid and consolidate to the same blocks, so never make either field required nor rewrite stored ops. A format change is a `modification`, shows its text once with words that say what changes (`FormatChange` codes, `common.content.format.*`; on screen a dotted line of its own hue and a note at the end of the block, never a chip inside the line, and a blank one only when it is the block's one change, `isShownFormatSegment`), never as a strike and a rewrite, and in overlaps takes its range (marks) or its whole block (`block`). Moving a block is still a delete and an insert; a table cell's fill and an image are not amendable.
- Status: `draft -> submitted ->` one of `approved`, `rejected`, `withdrawn`, `lapsed`, `transacted` or `inadmissible`. Each step is recorded in its own record:
  - admission, with `late` computed by the server;
  - the main presenter's position (`positionBlocker`, user's decision of 2026-11-17: once the main presenter sees it, so validated and published, or only validated when an office of the CEA presents the document, `presenterSeesValidated` from `loadAnswersOnValidation` in `executiveMembers.ts`, mirrored on the client by `AmendmentPositionContext.presenterSeesValidated`; a late one before the assembly admits it, its acceptance under `incorporate` incorporating it only once admitted, `positionEffect` and `incorporateOnAdmission`; also one the assembly already approved by a vote, by assent or as a formal one (user's decision of 2026-11-19: `answerableAfterDecision` in `shared/utils/positions.ts`, read by both `positionBlocker` and the client's `amendmentAnswerable`), and, since 2026-11-21, one rejected (accepting it does not approve it), whose new answer is only recorded (`position_changed`; `positionEffect` is null: no reopening, the outcome stays); such an amendment never waits for an answer, so it stays out of the review mode's queue and progress and of every count (`amendmentAwaitsPosition`, `countPositionsPending`), its detail shows the answer under the details with a secondary «Cambiar la respuesta», never as the presenter's turn, and `amendmentPositionNext` says `decided`; never after the final vote), with `PositionDto.recordedBy` saying whether someone recorded it on the main presenter's behalf (the `by` of the latest `position_changed` event, so it survives a change of main presenter) and `recorder` who: the Secretaría or the Presidencia by the role of the account that did, the Mesa otherwise (`positionRecorder`). Who gave an answer and when (`recordedBy`, `recorder`, `updatedAt`) reach only its authors, the document's presenters, the CEA's accounts, the Mesa, the Secretaría and the Presidencia (`seesAnswerRecord`, `toPositionDto`); everyone else who reads the answer gets them null. Sentences name the member by its name, never its acronym (`memberSpokenName`);
  - votes;
  - decisions;
  - acceptances.
- Amendments are numbered when they are presented (`numberAmendments` in `server/utils/domain/amendments.ts`, called by `submitAmendment` and `createTransactionalAmendment`, and again on publication for those presented before this rule): `number` per document and a code of the main author's prefix and its count in the document, with no space (`formatAmendmentCode` in `shared/utils/amendmentCode.ts`): `UGR1`, `ANEM3`, `CEA2`, and `T1` for transactionals. The prefix is the acronym the presenter's avatar reads (`amendmentCodePrefix`): a council's university acronym (`members.university_acronym`), else its own acronym; a sectorial's or the CAS's acronym; `CEA` for every office. Each prefix counts on its own in each document (a member whose prefix changed starts at 1), and a number once given stays taken whatever becomes of the amendment (withdrawn, a corrected draft deleted, a code given up by a change of main author): `nextMemberSeq`, `nextNumber` and `nextTransactionalCode` read every code the document's amendments hold or ever held (`takenAmendmentCodes`: the rows and the `code` and `previousCode` of their events). Codes from before keep their space (`CEUM 2`) and still count (`amendmentCodeSeq`). Only drafts, and amendments presented before this rule that nothing numbered yet, read without a code ("Sin número"; clients word it, never `code ?? ""`). A code names one amendment of the document (`amendments_document_code_unique`). `pnpm db:recode-amendments` (`drizzle/recode-amendments.ts`, `planAmendmentCodes`) recodes a database under today's rule, once, after the roster sync has brought the university acronyms (DEPLOYMENT.md).
- Presenting never admits. The Secretaría validates each amendment (admitting the on-time ones; late ones still need the Mesa) or sends it back with a correction note, and publishes it when validating or later. Only published amendments are visible beyond their authors, the Secretaría and the Mesa (`publishedAt`), with two exceptions: the CEA's accounts (role `CEA`) read every presented one from the moment it is presented, before its validation too (`seesPresentedAmendments` in `visibility.ts`; user's decision of 2026-11-19), and once validated (`validatedAt`) an unpublished one is also read by whoever reads the control sheet (`control_sheet:view` or `:edit`) (`seesValidatedAmendments`); neither reads its correction notes, and nobody answers one before its validation (`positionBlocker`, `not_validated`); the presenters of the amended document wait for its publication like everyone else (user's decision of 2026-11-17), unless they are the CEA. `canSeeAmendment` takes `AmendmentVisibilityContext.validatedAt`, so every loader passes it (`documentPresenters` still travels with it, read by no rule today). A withdrawn amendment is never public, published or not (user's decision of 2026-11-17): only its insiders, reviewers, the Mesa, the CEA's accounts and the control sheet's readers read it (`seesWithdrawnAmendments`), not even the document's presenters; counts that go by SQL (`countVisibleAmendments`) leave it to `canSeeAmendment`. Transactionals the Mesa presents, and late amendments it admits, are published at once.
- The Secretaría may take a validation back while the amendment is undecided, published or not (`can.unvalidate`, `validationReopenBlocker` in `reviewState.ts`): «Deshacer la validación» (`POST .../[amendment]/unvalidate`, `amendment_validation_undone`) puts it back in «Por revisar» as it is, still presented, no longer validated, published nor admitted; «Devolver para corregir» (`POST .../[amendment]/correction`, the same as before validation) sends it back to its authors as a draft with a note: they keep its number, code and timing and may fix it and present it again, on time if it was, while the document takes amendments, or leave it, since a draft never counts. Either way its presenter's answer goes back to pending. Never for a transactional, a late one the assembly admitted, one on screen, or one any transactional groups, closed ones included, which could come back over it (409 with a `messageKey`; `assertValidationReopenable`); both take `shareLockAssembly`, then the document FOR SHARE, and an optimistic lock on the amendment.
- When it does not validate an amendment, the Secretaría chooses whether it can be corrected (user's decision of 2026-11-19): «Pedir corrección» in Validación and on the amendment, and «Devolver para corregir», ask «¿Puede corregirla?» (`AmendmentCorrectableChoice`); «Sí» (the default) is the correction above, «No» declares it not admitted with the note (`POST .../[amendment]/correction` with `correctable: false`, `declareInadmissibleOnReview`; the button labels are unchanged). It takes one waiting for validation (late ones too), one validated that could go back to review except a late one (the assembly decides on those once validated, «No tratarla»), and a draft already sent back for a correction, which the reviewer closes with «No admitirla» on the amendment (`reviewInadmissionCase` in `reviewState.ts`, mirrored by `amendmentInadmissibleOnReview`). It becomes `inadmissible` (status and admission), decided now, with the note as `outcomeNote`, keeping its validation and publication as they were (one never validated stays private), and a returned draft gets back its `submittedAt` and `submittedByUserId` from its latest `amendment_submitted`; one validated has its answer reset. It records a `decisions` row (kind `inadmission`, method `secretaria`), `decision_recorded` and `amendment_inadmissible` with `onReview`, the note and `afterValidation`/`afterCorrection`/`positionReset`, so the `presenter_decided` email says it cannot be corrected with «Nota de la Secretaría» (`inadmissibleWording` in `server/utils/notifications/wording.ts`) and the news reads `home.news.amendment.inadmissibleReview` (`newsValue` "review"). The Mesa may readmit it (`POST .../admission`). Same locks as the correction. The Mesa's own inadmissions also store their note as `outcomeNote` and in the event (`note`), so its authors read why; readmitting clears it, and a failed vote to readmit keeps the reason given first.
- Who reads the main presenter's answers is decided per document (`canSeePositions`, `positionsArePublic` in `shared/utils/positions.ts`): its presenters, the Mesa and whoever reviews amendments always; everyone else once they are public. They become public for good when the debate of the document's agenda item starts in session: every writer of `live_state` that points it at an item or a document calls `stampDebateStarted` (`server/utils/domain/positionsPublication.ts`), which sets `documents.positions_debate_started_at` once on the published documents of that item (or that document), only while the assembly is `in_session`, and records `document_positions_debate_started` (nobody chose to publish: the Mesa only moved the projection). Before that the Secretaría (`document:manage`, never the Mesa alone) may publish them document by document and take that back while the debate has not started (`PUT .../documents/[document]/positions`, «Publicar las respuestas del proponente» in the document's «Más» menu; `positions_published_at`, `positionsUnpublishable`, 409 `document.positions.errors.debateStarted`). The assembly-wide `settings.positionVisibility` is gone (user's decision of 2026-11-17): a stored one is dropped when read (`assemblySettings`), its old changes still read in the activity, and migration 0038 kept public what it had made public.
- A deadline's own minute is on time (user's decision of 2026-11-20): a deadline at 23:59 takes everything sent during 23:59. Every deadline check goes through `isPastDeadline` in `shared/utils/calendar.ts` (the amendment window, `isLateSubmission`, `documentsDeadlinePassed`, `sentAfterDeadline`, `isDocumentOverdue`, the clients' countdowns and buttons), never a bare `>` on the date. What was sent before `DEADLINE_MINUTE_COUNTS_SINCE` keeps the earlier reading, so nothing already late changes (amendments store `late` anyway).
- Late amendments (`late`, computed on submission) stay `admission: pending` after the Secretaría validates them; once published they show as out of time until the Secretaría or the Mesa records the assembly's decision (`POST .../amendments/admission`). The validation inbox lists them, published or not, until then (`awaitsAssemblyDecision`). Only admitted amendments can be decided; a late one awaiting the assembly may be grouped into a transactional (see below).
- Those who review amendments (`amendment:review`; never `session:moderate` alone) can reclassify a presented, undecided amendment (one the main presenter's acceptance incorporated counts, `canReclassifyAmendment`) between "de forma" (`formal`) and the content kind (`partial`), the only two kinds with a counterpart (`reclassifyTarget` in `shared/utils/amendmentReclassify.ts`; `POST .../[amendment]/reclassify`, optimistic lock). It records `amendment_reclassified` (`{ from, to }`), which the history shows with the members before and after, and the authors read in their news.
- When the Secretaría says an amendment cannot be corrected (`correctable: false`, declared not admitted), its note is optional (user's decision of 2026-11-20): `amendmentCorrectionBodySchema` needs one only to send it back, and the forms (`ReviewCorrectionModal`, `AmendmentReviewPanel`, `AmendmentValidationUndo`) mark it «(opcional)»; without one the email and the outcome carry no note.
- Validación filters everything it lists by one document or one member presenting (a document's presenters, an amendment's authors), «Validadas» included (user's decision of 2026-11-20); filtered away, a section says it has nothing, never «Todo al día».
- Who may present a transactional is an assembly setting (`transactionalProposers`, user's decision of 2026-11-20): `involved` by default, the authors of the original amendments it combines and the document's presenters (`canProposeTransactional` with `isParty` over `originalAmendments`); `anyone` lets any member with `amendment:create` too; the Mesa always may. One presented by an author of what it combines keeps today's rule: the presenter answers after the Secretaría validates it and is no party. Applying an inclusion never touches the answer, so an accepted one stays accepted. The ones validated before this rule get it once at boot (`backfillProposedTransactionals` in `proposedBackfill.ts`, plugin `proposed-transactionals.ts`: it first fills `proposerMemberId` from the member of the latest `amendment_submitted` with `admission: "pending"`, then settles each candidate through `settleProposedTransactionals`, with the validator as actor; only the rows whose proposer that boot filled, marked `meta.proposerBackfilled` until the run ends, so a later restart settles nothing; the live paths are `POST .../validate`, an admission under `incorporate`, and a parent declared not admitted while the transactional goes on with the others). Never a content amendment, never after the final vote; a transactional its presenter presented is accepted by that presenter instead (`acceptProposedTransactionals`, above). It records `amendment_authors_changed` (`{ from, to }` with member ids, plus `code` and `previousCode` when the code changes), which the history shows and the authors read in their news.

They build only on published, submitted and undecided amendments, admitted or late and still awaiting the assembly's admission (user's decision of 2026-11-19; `isPendingLateSource` in `reviewState.ts`, `isLateAwaitingAdmission` and the console's `isSessionTransactable` on the client). One proposed by a member is `pending_authors` until every party accepts it (any rejection closes it as `withdrawn`), then goes to the Secretaría (`validate` answers 409 before that, and the inbox lists it read only). «Validación» lists the transactionals in a section of their own, «Transaccionales», above «Enmiendas», those to validate and those waiting for their authors (`splitReviewParts`' `transactionals`; user's decision of 2026-11-19); «Por revisar» never counts them. Validating a transactional always publishes it (`publishOnValidation`). Once validated and accepted, whichever comes last, it replaces its parents (they become `transacted`) and follows the normal flow; one the Mesa presents is validated and published at once and replaces them when the parties accept in the room. Replacing them closes every other submitted transactional over any of them (`lapsed`, reason `sources_transacted`): every path that calls `replaceSources` locks those competitors in the same ordered pass (`findCompetitors`). Settling a parent any other way (withdrawn, lapsed, declared inadmissible, voted, or incorporated by the main presenter's acceptance) closes the pending transactionals over it at once (`withdrawn`, `amendment_withdrawn` with `by: "sources_closed"`): every such path locks them in the same ordered pass and calls `closeTransactionalsOver` (`server/utils/domain/transactionalClosure.ts`). The closed transactional gets the parent's `decidedAt` and no `outcomeNote` (clients word the reason in the viewer's language from its parents), and its authors and parties see it in their news with nobody named (`by` null), also when their own act closed it. It is undone the same way: when that parent goes back to undecided before the final vote (the main presenter's answer changes, the Mesa reopens its decision, the rule goes back to `vote`, the assembly readmits it), the transactionals closed over it come back (`submitted`, `amendment_reopened` with `reason: "source_reopened"`, `sourceId` and `sourceCode`, news with nobody named) if their latest withdrawal is that automatic closure, every parent is open again (in whatever order they were reopened; a closure from before this rule too) and no main author rejected them (`transactionalsToRestore` and `reopenTransactionalsClosedBy`; every reopen path locks them and their other parents in the same ordered pass, `restoreLockIds`, then their acceptances). Reopening a transactional never restores its own parents, and one that never replaced them, or that a main author rejected, cannot be reopened (`transactionalReopenBlocker`). In the Mesa console a one-click decision that would close a pending transactional over the amendment (assent, de forma, withdraw, lapse, or acceptance where accepted amendments are incorporated) asks first, in the same dialog as the not-in-debate question, and says that reopening the amendment before the final vote brings it back unless another of its parents was decided (`sessionPendingTransactionalIds`, mirroring `transactionalsToClose`; `confirmSettling`), and the card of a closed one says so only while that holds (`isSessionClosureReversible`); "Ahora en debate" and the vote, admission and lapse dialogs name it and who it waits for (`useSessionTransactionalsOver`), and bulk assent (`sessionAssentPlan`) leaves out amendments with one pending (`transactional_pending`) and those that collide with one left out of the batch (`transactional_clash`).

A read creates nothing; the first write or sync makes the plan and the Mesa's group with its usual people (`MESA_DEFAULT_LABELS`: at an AGO «Presidencia de la Mesa» and «Vocalía de la Mesa» as placeholders to name; the Secretaría is the SE attendee). Seat ids are stored in the layout, never derived.
- Names and photos of attendees are personal data: they leave the server only in the seating answers to seating readers (`requireViewer` first, so `?view=room` is refused), never in an event or audit payload, a log, a live message, a notification or another section's export. A failed query's error carries its parameters (drizzle's message and stack end with them), so the seating handlers never use `throwMutationError`: `throwSeatingError` (`server/utils/seating/errors.ts`) logs only the error's name and its SQLSTATE. Seating texts drop control characters (Postgres refuses a NUL), from a body or from the Intranet. The view names the offices and who acts for them, so both keys are in `EXECUTIVE_VISIBLE_PERMISSIONS`; group members still go through `redactMember`.
- Lock order, everywhere: `shareLockAssembly`, then the plan row, then the assignment rows. A layout save, a sync's write, the source and every group or person write take the plan FOR UPDATE; an assignment batch takes it FOR SHARE, then its rows in seat order FOR NO KEY UPDATE. A batch (`POST .../seating/assignments`, up to 600 ops, `checkAssignmentBatch` in `server/utils/seating/assignments.ts`) compares each seat with `expected`, deletes the rows it saw on the seats it changes (locked, never a seat it saw empty: a row another batch put there meanwhile was never compared, and inserting over it fails instead) and inserts the new occupants; a mismatch, a person sent to a second seat the batch does not empty, a person marked «No necesita asiento» or gone from the plan (`unknownPersonIds`), a seat the layout lacks or disables, or a race with another batch answers 409 `seating_stale` with who sits there now. A layout save (`PUT .../seating/layout`) checks `layoutUpdatedAt` (null only while there is no layout) and answers 409 `seating_seats_occupied` with the people on the seats it removes or disables unless `releaseSeats` confirms every one of them, seat and person, as that 409 named them (`releaseConfirmed`, the precedent of `isDeactivationConfirmed`): anyone seated there since answers the same 409 again with the new list; the confirmed ones go back to the tray in the same transaction. Groups and people take `updatedAt` on PATCH (409 `seating_stale` with the row); the source a compare-and-set on `expected` against the plan row once locked (made if missing), never a row read before it existed.
- The sync (`POST .../seating/sync`, `syncSeating`) reads `GET {base}/asambleas/{type}/{number}/asistentes` for the assembly's type and number, or those of `sourceAssemblyId` (`server/utils/seating/intranet.ts`, with the token, never logging a name). It calls the Intranet at most once a minute per assembly (a compare-and-set on `syncedAt`, the time of the last call whatever it answered) and never inside a transaction. It always answers 200 with the plan; `plan.sync.status` says how the call went: `ok`, `not_found` (exactly `{"error":"not_found"}`: no event carries the pair; the page offers another assembly's attendees), `unavailable` (any other 404: the Intranet does not have the route yet; the plan works with groups made by hand and its line says nothing, editors keeping only «Sincronizar»; a sync pressed by hand says it in a toast), `failed`, `unconfigured`. The route has a rate limiter bucket of its own (`SEATING_SYNC_RATE_LIMIT`): a change of source starts its minute again. Only `ok` writes groups and people (`planSeatingSync` in `server/utils/seating/syncPlan.ts`): by `intranetAccountId` and `intranetAttendeeId`, `memberId` by `members.intranetId`, `goneAt` on what is no longer listed and cleared when it comes back, only rows whose Intranet fields changed; never `needsSeat`, `label` or `position`, never manual groups, manual people or placeholders, never an assignment. `seating_synced` (status and counts) is recorded only when the status or a row changed. The page syncs when it opens and the last sync is over 10 minutes old, for editors only.
- Images (`server/utils/seating/images.ts`): each sync queues the logos and photos whose version changed on the pg-boss queue `seating-images` (the export queue's instance, `server/plugins/seating-images.ts`, 4 at a time); a job fetches the image from the Intranet with the token, caps it at 5 MB and writes a 192 × 192 WebP with sharp (photos cropped to a square, logos fitted on white) to `UPLOAD_STORAGE_DIR/seating/<planId>/<kind>-<id>-<version>.webp`, then names it on its row, under the plan's row FOR SHARE (a sync holds it FOR UPDATE while it reads and writes the rows), only if the version is still the one fetched. An SVG logo is any file an Intranet account uploaded, and librsvg's work is bounded by neither its bytes nor its pixels: it is rasterised in a separate Node process killed after 10 s, one at a time (`renderSvgInProcess`, `server/utils/seating/svgRender.ts`, as `renderPdf`), never in the app's process. A version that changes or turns null, or a row that goes, loses its file at the sync (written even when the row read had none). `GET .../seating/images/[file]` serves only a file a row of this assembly's plan names now, of the row's version, `private, max-age=31536000, immutable`, with its own rate limiter bucket; the DTOs give its URL on the same terms. A version that fails for good (a 404, over the size cap, unreadable) is remembered in this process's memory and not queued again until the Intranet's version changes (`server/utils/seating/failedImages.ts`); a timeout or a 5xx throws and pg-boss retries it. A new image arriving sends a live `seating_images_ready` (no history row). The 30-day retention of photos is not built yet.
- Every write records an event of entity `seating` whose entityId is the plan: `seating_synced`, `seating_layout_updated` (counts and template kind), `seating_assignments_changed` (placed, moved and removed counts, member ids), `seating_group_*`, `seating_person_*` (ids, kinds, source and the names of the fields changed, never a value) and `seating_source_changed`. They are in `IGNORED_LIVE_ENTITIES`, so a moved seat never refetches the hub; the activity shows them only to seating readers.
- The page (`app/pages/asambleas/[assembly]/sala.vue`, `app/components/seating/*`, `app/composables/seating/*`) draws the room as one SVG (`SeatingPlan`, pan and zoom in `useSvgViewport`, its maths in `-viewport.ts`) in «Cuentas» (one capsule per block of an account) or «Asistentes» (one bubble per seat), «Ver» for readers and «Colocar» and «Editar sala» for editors. Colours come only from `seatingGroupColour` through `SEATING_COLOUR_STYLES` (`-model.ts`), on rings and tints, from the group's kind and Intranet type together: burgundy (`primary`) for the CEA and the Mesa, green (`sectorial`) for the sectoriales and the CAS, blue (`info`) for the asociados and the CAI, beige for the CdG, the guests and every other account (`--seating-beige` in `main.css`, 4.3:1 on the light floor and 6.3:1 on the dark one; user's decision of 2026-11-15), grey only for a seat whose group the plan lost; text stays neutral. Pending registrations are dashed in both views; a free seat's outline reaches 3:1 on the floor. The plan is one tab stop with a roving focus along the runs (`stepSeat`, `jumpRun`), whose ring shows whenever the last input on the page was a key (a Tab into the plan, Enter in the tray); every seat has a label («Asiento 12, U exterior: UGR, Ana Pérez»), and «Lista» («Más») is the same room as text, the accessible equivalent and the phone's fallback: while someone is being placed each of its seats offers «Colocar aquí». «Editar sala» keeps a draft apart from the fetched plan (`useSeatingLayoutEditor`): the Doble U's numbers regenerate it keeping seat ids (`regenerateKeepingIds`), loose chairs and disabled seats, «Guardar sala» under the layout's lock, held back (as «Usar esta disposición» in the gallery) while a number on screen makes no room (`DoubleUFields`' `valid`). Editors sync on opening when the last call is over 10 minutes old (`syncDue`); the page refetches, debounced, on its own live events (`affectsSeating`).
- «Colocar» never drags (WCAG 2.5.7): the tray (`SeatingTray`, «Sin sentar», «En parte», «Sentados» folded; a drawer on a phone) or a seat picks an account or a person (`trayPick`, `personPick`, `unitAt`: the block along the run in «Cuentas», the person in «Asistentes»), and a tap or Enter on a seat lands it where `placementTarget` (`app/components/seating/-placing.ts`) says: seats in a row, never on both sides of someone, green when everyone fits, red otherwise («Colocar los que caben»); onto another block of the same size it swaps, onto anything else it asks («Intercambiar»: they take the seats left; «Desplazar»: they go back to the tray). The preview is said in words over the plan too, never by colour alone. Every change of who sits where is one batch built with `assignmentOps` over the room as the page has it (`useSeatingPlacing.apply`), never in place: a 409 `seating_stale` refetches and says so. «No necesita asiento» is the person's PATCH alone (the server frees the seat). «Proponer reparto» is `proposeSeating` worked out again over the live plan and drawn as a ghost until «Aplicar»; «Rehacer todo» also moves whoever sits at free tables or on loose chairs. The CAS (kind `cea`, a CEA account in the Intranet) sits right after the sectoriales, never in the `cea` zone (`CAS_SITS_WITH` in `shared/utils/seating/groups.ts`, user's decision of 2026-11-15; `compareSeatingGroups` ranks it there too). The warnings are `seatingWarnings`, worded. A Mesa person is linked only to the viewer's own account («Es mi cuenta»): no list of platform accounts reaches a seating editor, and the server refuses (422) a link to another account or on a person outside the Mesa; a link already stored stays, and null unlinks it. A person or group dialog refused as stale keeps what was typed over the row the 409 returns; one whose row is gone (404 `seating_not_found`) closes and the plan refetches. The live region says each change («UGR (3) en los asientos 12 a 14 de la U exterior», `seatRanges`).

### Email notifications

- What is notified by email, to whom and how often is data, edited at `/admin/notificaciones` (`notification:manage`, held by the Secretaría and the Presidencia through every key): one row of `notification_settings` read over `DEFAULT_NOTIFICATION_SETTINGS` (`readNotificationSettings`), with a general switch and, per kind (`NOTIFICATION_KINDS` in `shared/constants/notifications.ts`), on or off, the roles it goes to (the `roles` audience) and the frequency (`immediate`, one email per notice; or `daily`, one summary per account at 08:00 Madrid, pg-boss queue `notifications-digest`). Every notice is `immediate` by default except `amendment_submitted`, `daily`: amendments come in bursts before the deadline. Saving uses optimistic locking and writes `notifications.update`; the test email writes `notifications.test`. Never hardcode who gets a notice.
- The `presenters` audience is never a setting: the accounts linked to the members a document or an amendment concerns (its presenters, its authors, a transactional's parties). Nobody is told about their own act: never the account that did it, and for those notices no account of the member that did it; what an Admin did while impersonating an account reaches it, as in the news.
- `recordEvent` puts every event that may notify (`eventMayNotify`, `server/utils/notifications/triggers.ts`) in `notification_outbox`, in the transaction of the change. Never send an email from inside a transaction or a request: the sender (`server/utils/notifications/runner.ts`, woken by the live hub's LISTEN and every 30 s) reads the outbox once committed, plans one `email_deliveries` row per account and notice (`noticesForEvent` in `rules.ts` is the rule, pure; `planDeliveries` in `plan.ts`; `dedupeKey` unique per account) and sends them with retries. A transactional reaching the Secretaría is told once whichever path gets it there (`transactional_ready:<id>`).
- An email is composed when it goes (`composeNotice`, `server/utils/notifications/compose.ts`) as its account sees things then: `canSeeAssembly`, `canSeeDocument`, `canSeeLoadedAmendment` (otherwise `not_visible`) and `visibleAcronym`, so the offices read as "CEA" for whoever may not see them. It carries the code, the title, who presents it, a correction note to the presenters it was written for, and a link; never the text of a document or an amendment. The stored row keeps the subject once sent, never the body nor the address; the log shows the subject only to `document:manage`.
- Every subject starts with its assembly in brackets, `[80.ª AGO]` (`EmailNotice.tag`, `formatAssemblyLabel`; a summary names each of its assemblies once), so the inbox tells assemblies apart. Composers write the subject without it.
- Emails are in Spanish only, like the web's transactional emails, drawn like the platform (`server/utils/notifications/template.ts`: Raleway with lining figures, slate neutrals, `creup-red-900` for the button and accents, the assembly as a badge, a card with the light logo `public/marca/correo-cabecera.png`; tables and inline styles, everything escaped, a plain text part). A daily summary lists its notices with links, not one button each. Their copy lives in `compose.ts`, not in `i18n/locales`; the admin page is UI and goes through i18n as usual.
- Logs carry `accountRef` (`emailFingerprint`), never an address, and SMTP errors go through `describeSmtpError`.

### Private notes

- Each account keeps private notes on a published document (`document_notes`; `server/utils/domain/documentNotes.ts`, `shared/utils/documentNotes.ts`): about the whole document, or on a stretch of one block of its text (block id, character offsets into the block's text as it shows, and the text it covered, `quote`). They are the account's own (a council's account shares them): every read and write is keyed by `actor.user.id`, and no endpoint returns another account's.
- An Admin acting as the account is that account here too: it reads and writes its notes, and what it writes is recorded under the impersonation. The activity records only that one was written, changed or deleted (`document_note.*`, payload `anchored`), never its text nor where it is. Never add either to a payload, a log or an export.
- Nothing follows the document: when the text is published again, `locateNote` looks the quote up in the block, and a note it cannot place stays listed with its quote ("Sin ubicación"). Never delete notes because the text changed.
- `DocumentNotes` is the whole UI (the "Notas" button, the side panel, the dialog, the marks on the text), on the document page and in the reader of an agenda item. The marks are drawn with the CSS Custom Highlight API (`::highlight(cx-note)` in `main.css`) over the text ContentView renders: never write a note into the rendered HTML. "Añadir nota aquí" is in the text's right-click menu (`AmendmentTextActions`), next to "Hacer enmienda aquí"; selecting text with a mouse or the keyboard shows both in a small bar over the selection (`-selectionBar.ts`), never on a touch screen (the system's selection menu sits there) and never taking the focus.
- Each account also keeps private notes on an amendment it reads, past draft (`amendment_notes`; `server/utils/domain/amendmentNotes.ts`, `shared/utils/amendmentNotes.ts`), always about the whole amendment (user's decision of 2026-11-17: an amendment is short and its diff changes with the view). Same rules: keyed by `actor.user.id`, the amendment from `loadAmendmentContext` (404 for one the account may not read), `amendment_note.*` audit rows on the amendment's document with no payload, never the text. `AmendmentNotes` («Mis notas», under the panels that are the viewer's turn in `AmendmentDetail`) is the whole UI.
- An account that edits the control sheet (`control_sheet:edit`: the CEA, the Mesa, the Secretaría, the Presidencia; user's decision of 2026-11-17) may send a new note to the amendment's observations in the sheet instead («Observación en la hoja de control»): `PATCH .../control-sheet/amendments/[amendment]` with `observationsAppend`, which adds it below what the sheet says, a blank line apart (`appendObservations`), never in its place, so it takes no lock token and the earlier text stays in the row's history; 422 `control_sheet_observations_too_long` past `CONTROL_SHEET_OBSERVATIONS_MAX_LENGTH`. The form says that every reader of the sheet reads it. Whoever reads the sheet reads its observations about a document on the document's page as well, read only: those of its agenda item and its amendments in the «Notas» panel, each amendment's under its «Mis notas» (`GET .../control-sheet/documents/[document]`, `loadDocumentSheetObservations`, `ControlSheetDocumentObservationsDto`, provided once by the page through `provideSheetObservations` and refetched on `control_sheet_observations_updated` or a poll, `affectsSheetObservations`; the stream does not say which document a sheet row is about); nobody else ever gets them there.
- The control sheet shows each account its own general notes (user's decision of 2026-11-21) through `GET .../control-sheet/notes` (`server/utils/domain/sheetReaders.ts`). That endpoint is keyed by `actor.user.id` like every other, and filtered to the published documents the account sees and the amendments past draft it may read (`canSeeLoadedAmendment`). Anchored notes are only counted there.

## Traceability And Impersonation

Model in [`docs/design.md`](docs/design.md) ("Traceability", "Impersonation"); endpoints in [`docs/api.md`](docs/api.md) ("Activity and impersonation").

- Every mutation calls `recordEvent` or `recordAudit`, directly or through a server function. Never insert into `audit_log` directly: `recordAudit` (`server/utils/domain/audit.ts`) is the only writer. `server/utils/domain/traceability.test.ts` enforces it; an endpoint that writes no state goes in its commented `NON_RECORDING_MUTATIONS` allowlist.
- Identity comes only from `getAuthUserWithRole`, `requireActor` or the RBAC callers on the server and from `useMe` on the client, never from `session.user` or `authClient.useSession`: while an Admin impersonates, the session is still the Admin's.
- Impersonation is Admin-only by the real role through `requireAdmin`, never a permission key. Never as oneself or another Admin, never as an account without access (403 `targetRevoked`), never nested, 60 minutes fixed, with a reason. An open impersonation of an account that loses access ends as `revoked`. The admin section, `/api/members` and `/api/calendar-rules` are read-only while it lasts, and every unsafe request sends `x-acting-user`.
- Events recorded with `actor: null` inside an impersonated request pass `impersonationId` explicitly.
- The Intranet writes with source `intranet` and actor null: `user.access_revoked`, `user.access_restored` and `user.intranet_missing` at sign-in, `user.access_revoked` and `users.access_recheck_blocked` in the daily access re-check, and the daily roster sync's `members.sync` rows and `members.sync_blocked`. A manual roster sync keeps the account that ran it as actor.
- Update events put what changed in `payload.changes`, built with `diffChanges` (`server/utils/domain/changes.ts`) from the stored row against what was written, never from the request body; never content blocks or correction notes. Delete events carry an explicit allowlist that names the entity and its insiders; never spread the row into a payload.
- Read activity only through `server/utils/domain/activity.ts`. A new event type, audit action or payload key goes into `shared/constants/activity.ts` and into `EVENT_PAYLOAD_KEYS` or `AUDIT_PAYLOAD_KEYS` (otherwise non-Admins see nothing of it), with an `activity.actions.<action>` key in both locales and an icon in `ACTIVITY_ACTION_ICONS`. Linked messages (`@:key`) may reuse existing wording.
- Scripts that write to the database outside Nuxt (seed, one-off loaders) write audit rows with the exact `recordAudit` shape (source `seed` or `import`). The seed may import `audit.ts`, so keep its runtime imports to packages and `../../db/schema`.
- IP addresses and user agents in `audit_log` and `impersonations` are personal data; there is no retention job yet.

## API Rules

Typical handler order:

1. `requireAuth`, `requireAdmin` or `requirePermission`.
2. Validate route params. Use slug resolvers when routes accept slugs; otherwise use `validateCuid` or `validateAuthId`.
3. Validate query/body with Zod.
4. Run DB work.
5. Return minimal stable JSON.

Rules:

- Use `createError({ statusCode, message })`, not plain errors.
- User-facing API messages should be Spanish unless routed through i18n.
- Keep handlers small. Extract complex logic to `server/utils/`.
- Do not expose internal DB fields unless the client needs them.
- `/api/admin/**` opens by permission: users, their roles, member links and grants need `user:manage_roles`; roles and the permission catalog need `role:manage_permissions` (reading roles needs either); the statistics need `stats:view`; the email notifications need `notification:manage`. Each endpoint checks its own with `requireAnyPermission`, and only an Admin gives or takes the `Admin` role. A non-Admin never raises its own access nor locks itself out: not its own role, its own account's grants or member link, not `user:manage_roles` or `role:manage_permissions` taken away from the role it holds, and no key it does not hold itself (`adminGrantViolation`). The last Admin cannot leave the `Admin` role.
- All mutation endpoints need CSRF header and same-origin protection.
- Client mutations must include `CSRF_HEADER_NAME` from `shared/constants/security.ts`.
- That protection comes from the `serverHandlers` middleware in `nuxt.config.ts`:
  `server/handlers/auth.ts` for the admin section, `server/handlers/protected.ts`
  for the authenticated non-admin sections. A new API section needs its own
  entry, or its mutations run unprotected.
- Middleware routes must be a plain prefix (`/api/assemblies`), never
  `/api/assemblies/**`. Nitro registers them with `h3App.use(route, ...)`, which
  prefix-matches literally, so a `/**` suffix silently never matches and the
  middleware never runs.
- `/api/auth` is deliberately left uncovered: the Google OAuth callback is a
  cross-origin POST.
- The CSRF cookie is issued by `server/middleware/csrfCookie.ts`, which runs on
  every response including the page render. Issuing it from an API handler is
  not enough: during SSR those run as internal `$fetch` calls whose `Set-Cookie`
  never reaches the browser.

Client mutations go through the shared client, which adds the CSRF header and
`x-acting-user` (`ACTING_USER_HEADER_NAME`, the account the page acts as):

```ts
const api = useApi();
await api.send(url, { method: "POST", body });
```

A raw `$fetch` with only the CSRF header gets 409 `auth.identityChanged` for any
real Admin. Server section handlers match paths on the full decoded original
URL, never on `event.path` (h3 slices the prefix, and `/api/me` also matches
`/api/members`).

## Error Pages

`app/error.vue` renders only localized copy, keyed off the status code. Never
render `error.message` or `statusMessage`: on a 5xx that is the server-side
exception, and on a 4xx it is untranslated framework or handler text.

Pages that need their own wording pass an i18n key:

```ts
throw createError({
  statusCode: 404,
  data: { messageKey: "assembly.notFound" },
});
```

## Database And Migrations

- CUID2 primary keys use `text('id').primaryKey().$defaultFn(cuid)`.
- Timestamps use timezone-aware `timestamp({ withTimezone: true, mode: 'date' })`.
- `updatedAt` should use `.$onUpdate(() => sql\`now()\`)`.
- Self-referencing FKs may require raw SQL migrations.
- Edit schema files first, then run `pnpm db:generate`.
- `drizzle/meta` is tracked, not ignored. `db:migrate` reads the journal to know
  what to apply and `db:generate` diffs the snapshots to emit the next
  migration, so a clone without it can do neither. Commit what drizzle-kit
  writes there; never hand-edit or reformat it.
- Do not edit existing migration files after they have been committed.
- A release must still run on the schema of the next one: the previous
  release keeps running while the migration applies, and after a
  `scripts/rollback.sh`. Drop or rename a table or column, or change the
  shape of a JSON column (`calendar_rules.quorum`, `assemblies.settings`,
  payloads, operations), one release after the code stops reading the old
  form, never in the same one; until then write or read both. Precedent:
  0021 dropped `headcounts.call` and changed `calendar_rules.quorum`, which
  the previous release read. For `users` it is mandatory: better-auth selects
  every column of the row on each request. `users.onboarding_seen_at` is
  unused and waiting to go.
- The image ships `drizzle/meta/_journal.json`: `scripts/rollback.sh`
  compares it with `drizzle.__drizzle_migrations` and refuses, without
  `--force`, an image older than the database. `scripts/deploy.sh` dumps the
  database (`backups/db/asambleas-predeploy-<date>.dump`, the last 10 kept)
  before migrating and stops if the dump fails; DEPLOYMENT.md "Restaurar"
  says how to restore one.

## PDF Export

Flow:

1. `POST /api/assemblies/[assembly]/export` or `POST /api/assemblies/[assembly]/documents/[document]/export` creates a pg-boss job. Queues are created on boot (`createQueue`).
2. The worker loads the data (`buildData.ts`) and builds the pdfmake definition (`pdfBuilder.ts`); pdfmake lays it out and renders it in a separate Node process (`renderPdf`, `server/utils/export/pdfRender.ts`, like the DOCX converter), with its own heap ceiling (`PDF_RENDER_LIMITS`), a timeout and an env allowlist, one render at a time across both queues (`withRenderSlot`), so the room keeps answering while a PDF is made. Never use worker_threads. The definition crosses as JSON: every function in it comes from `pdfFunction` or `constantLayout` (`pdfSerial.ts`), and `serializePdfDefinition` refuses anything else. A render out of heap, time or room is not retried (`PdfRenderLimitError`); one the kernel kills is. The worker logs `export-worker.timing`. Never replace `pageBreakBefore` with unbreakable stacks: pdfmake silently clips what does not fit on a page. The assembly dossier (`POST /api/assemblies/[assembly]/export`) needs `assembly:manage`, checked again by the worker.
3. Worker writes metadata and PDF to `EXPORT_STORAGE_DIR`.
4. Client polls `GET /api/exports/[jobId]/status`.
5. Client downloads through `GET /api/exports/[jobId]/download`.

Security and reliability:

- Download/status must verify the requester is the job owner or has the required permission.
- Do not store generated PDFs only in memory.
- Include `EXPORT_STORAGE_DIR` in backups.
- Keep PDF labels localized and use shared assembly/date formatters.
- Raleway font files must be available from `server/assets/fonts` after build, and the letterhead logos from `server/assets/brand`.
- Every PDF follows the reader's text alignment (`justified` in the job and the package's format, true when absent; `PdfContentContext.justify`, never inside a table's cells). Justifying never moves a line or a page break (`pdfPages.test.ts`), so `pageLayoutKey` does not carry it; package pieces do (`pieceKey`'s `es:ragged` layout, variants `pdf-ragged` and `editable-ragged`), and only justified packages are built ahead.
- The template's approval line ("Aprobada por [Mayoría] en la … el [Día] …") is recognised by `shared/utils/content/approvalLine.ts`, shared by the Word import (`templateHeader.ts`, `DocxImport`) and the PDF export: a document's PDF fills an unfilled one from the final vote that approved it (and then skips its own vote line) or leaves it out before; the stored text never changes.
- A Word table keeps its width, place and rules (user's decision of 2026-11-24; `docs/design.md`, tables): the converter reads the table's `tblW` (twentieths of a point, fiftieths of a percent or a percentage, else the sum of its columns) against the text width of the body's last section, its `jc` or, without one, its `tblInd` (centred when the room left and right is about the same), and its `tblBorders` and each cell's `tcBorders` (`docx-table` and `docx-borders` runs, `tableSpec`/`bordersOf` in `server/utils/content/docx.ts`); `tableBorders` in `docxHtml.ts` works out each cell's sides on the grid before `tableGaps` splits anything. A table that sets no rules of its own (a style's, which the converter does not read) keeps the thin rule everywhere, so imports of ordinary tables do not change. A table of one column stays a table only when it has a width or rules of its own (`keepsLayout` in `shared/utils/content/editor.ts`: a signature's line), and none of its cells becomes a header by its bold text.
- A Word file's blank lines stay as empty paragraphs (user's decision of 2026-11-24; `ignoreEmptyParagraphs: false`, `blankParagraphs` in `docxHtml.ts`, `data-blank`): the room a document leaves, a signature's above all. Only among the text's own paragraphs, never at its start or end; one in a cell, a list, a quote or a note goes. The template header (`templateHeaderLength`, which takes the blank lines among and right after it) and the approval line (`fillApprovalLines`, whose first blocks count no blank line) look past them.
- Tables a Word file lays side by side as one table, with an empty spacer column whose cells hide their top and bottom rules (the budget's income and expenses summary), are imported as tables one after the other, left to right, never as one table nor as a side-by-side layout block (user's decision of 2026-11-19; `tableGaps` in `server/utils/content/docxHtml.ts`, fed by the converter's `docx-gap` run, warning `tables_split`). Keep the detection conservative: an interior column, blank and unfilled in every row, that no span crosses, in a table of two rows or more, each part two columns wide with text; the rows that only pad a shorter part at its end go, never a blank row between a part's data rows (the rows after it would fall out of line). A table that marks headers by dark fills makes its other cells no headers (`data-header="false"`) only after the split, so each part decides by its own fills. The Word export (`buildDocumentDocx`) writes an empty paragraph between consecutive tables, or Word joins them into one.
- The documentation package ("Descargar documentación", `ExportPackageDialog`, followed in the background by `usePackageDownload`, so the dialog may close while it builds and a toast offers the download; `docs/api.md`, "Documentation package") is a ZIP of everything the assembly has published, the same for every account that sees the assembly: the convocatoria (the signed one, else `buildConvocationPdf`), the agenda (`buildAgendaPdf`) and a folder per numbered item with its published documents (uploaded PDFs as they are; each text as presented, without approval line, and its consolidated text once voted, as PDF and, when asked, as Word through `buildDocumentDocx`) and their published amendments, one PDF each on CREUP's amendment template (`buildAmendmentPdf`). It is built only from what a public reader reads (`loadPackageSource` with `publicExportActor`): never from the requester's actor, never with anything unpublished. Each file is a piece keyed by everything it shows (`planPackage`, `PACKAGE_RENDERER_VERSION`, bumped whenever a template changes), rendered once and kept under `EXPORT_STORAGE_DIR/packages/` (rebuildable, no backup needed); a build (pg-boss `assembly-package`, policy `stately`) renders only the missing pieces, one after another (a document's amendments in batches through `renderPdfBatch`), and writes the ZIP stored and streamed. Changes to a convened or sitting assembly build its Spanish packages ahead (`server/plugins/assembly-packages.ts`). An earlier ZIP is handed out while the current one builds only if all of it is still public as it was (`packageStillPublic`). Its filters take a part (user's decision of 2026-11-20; `filter.ts`, docs/api.md "Parts"): some documents, with or without their texts, and all, none or some of their amendments (by who signs them, as the public reads it, or the control sheet's list), without the convocatoria and the agenda. A part is the whole plan's entries filtered, never planned or built on its own: same paths and keys, zipped from the pieces while it downloads, its pieces rendered by the whole package's build. The dialog is also opened ready filtered: «Descargar» on an agenda item's page (its subtree's published documents), «Descargar con enmiendas» in a document's «Más» (beside the annotated PDF), and «Descargar» beside each control sheet list's filters (what the list shows: «General» its rows' published documents, «Enmiendas» the amendments it shows, without the text). Both menus are searched by typing; the members' one puts a council's university first and its acronym and denomination below (the one exception to `memberMenuItem`'s acronym first, user's decision of 2026-11-20).
- Page numbers of the web text (user's decisions of 2026-11-21): the readers (the document's tabs, «Consolidado», the agenda item reader, the Directo document window; not the projection nor the Mesa's panel) show «pág. N» where each page of the clean Spanish PDF with letterhead starts (the package's and «Exportar PDF»'s), numbered as its footer prints it (a positioning's cover uncounted), and a «Página X de N» in the text's bar (`ContentPageIndicator`, also on phones, where the marks hide). «Texto original», «Con la enmienda», «Comparar» and «Con lo aprobado» before the final vote take the text as presented's PDF, on the original's blocks only (an inserted block has none; a start whose block the view leaves out moves to the next one shown, `shared/utils/content/pageMarks.ts`); «Con lo aprobado» once voted and «Consolidado» the consolidated PDF's, recomputed for a corrected or conciliated version; side by side, only the original's column. English shows the Spanish numbers; the marks are not links. The maps come from the package's own renders, else from the `document-pages` job (`server/utils/export/documentPages.ts`), and are stored per version (`document_page_maps`) with a key of everything that moves the layout (`pageLayoutKey`: version, title, kind, the final vote as printed, the notes of passages pending conciliation, the assembly, the language, `PACKAGE_RENDERER_VERSION` and `PAGE_MAP_VERSION`): a map whose key no longer matches is never shown. Pages are read after layout from pdfmake's node positions, never from the `pageBreakBefore` callback (its `pageBreakCalculated` sticks across re-layouts); inside a table's unbreakable rows only the first position of a node with an id is put back on its page, which is why every tagged text gets a `pgtag-` id and a header row's blocks (repeated on every page) take the next row's page. Bump `PAGE_MAP_VERSION` when how pages are read changes. That reading relies on pdfmake's internals (`positions` corrected only for nodes with an id, `js/PDFDocument.js` and its `addNamedDestination`, patched by `pdfRender.ts`), so `pdfmake` is pinned to an exact version in `package.json`: a pdfmake or pdfkit upgrade must pass `server/utils/export/pdfPages.test.ts` (pdf.js reads each page of a rendered fixture). In a convened or sitting assembly the `document-pages` job waits past the package's prebuild (`pagesJobStartAfter`, `package/prebuild.ts`) and checks the stored map again once it holds the render slot, so the same PDF is not rendered twice; a reader asks again while it is pending, further apart each time, for up to 15 minutes (`pagesRetryDelay`).
- Exports follow CREUP's document template (`server/utils/export/brand.ts` and `CONTENT_STYLES`): logos in the header, a band down the left edge naming the kind of document ("Documentación interna", "Moción Interna", "Normativa propia", "Posicionamiento", "Resolución"), website, email and page count in the footer, and the title alone above the text. Level 1 headings sit on a burgundy bar and level 3 in a burgundy box, in exports and in the platform (`--content-heading` in `main.css`); positionings open with a cover page. Logos are PNGs because pdfmake embeds an image once but redraws an SVG on every page; the band's label is drawn as glyph outlines with `fontkit`, since pdfmake's SVG text cannot reach fonts in its virtual file system.

pg-boss v12 reminders:

- `work(queueName, { batchSize: 1 }, handler)` receives `Job<T>[]`.
- Queues must exist before `send` or `work`: create them on boot with `createQueue` (idempotent).
- `send(queueName, data)` returns a job ID.
- `getJobById(queueName, jobId)` requires queue name first.
- Common states: `created`, `retry`, `active`, `completed`, `cancelled`, `failed`.

## Security Checklist

- Auth required for all non-auth routes.
- Permission checked server-side for every protected operation.
- Admin APIs are not protected by UI checks alone: each one checks its permission server-side.
- Route params and body/query data validated before DB access.
- Mutations include CSRF and same-origin checks.
- Document content stored as validated blocks and rendered escaped; no raw HTML in `v-html`.
- Uploaded PDFs validated by type and file signature.
- Optimistic locking applied to shared updates.
- Unknown permission keys rejected, not silently ignored.
- Export downloads authorized.
- Every mutation leaves an event or an audit row (`recordEvent` / `recordAudit`).
- nuxt-security's `xssValidator` stays off: Zod, `blocksSchema` and escaped rendering cover XSS, and it refused plain texts such as «<<Ley>>» or «>50 %». Its rate limiter counts per IP plus the matching route rule, so it is off for `/api/assemblies/**`, `/api/exports/**` and `/api/me/**` (a whole room shares one IP); uploads, export requests, documentation package downloads, the room's cached images, the accounts' stored photos and the room's sync with the Intranet keep buckets of their own (`UPLOAD_RATE_LIMIT`, `EXPORT_RATE_LIMIT`, `SEATING_IMAGE_RATE_LIMIT`, `AVATAR_IMAGE_RATE_LIMIT`, `SEATING_SYNC_RATE_LIMIT`, `PACKAGE_DOWNLOAD_RATE_LIMIT` in `nuxt.config.ts`; asking for the documentation package shares `EXPORT_RATE_LIMIT`). A new endpoint there that reads uploads or queues work gets its own `rateLimiter` rule, or it inherits `false`. Never put a security header in a plain `headers` route rule (nuxt-security turns it into a bucket of its own; use `security.headers`). `server/securityRules.test.ts` replays the module's rule resolution: keep it in step with `nuxt.config.ts` and re-derive it when nuxt-security is upgraded.
- The CSP allows `connect-src` `https://127.0.0.1:*` and `wss://127.0.0.1:*` and `frame-src` `afirma:` on every page, for AutoFirma (the acta de acuerdos is signed from its page, and a client-side navigation keeps the CSP of the page the app was loaded on). Nothing else is framed.
- The projection reads as the room (`?view=room`, `requireViewer`): only the Mesa may ask for it, and the answer is what an account that sees only what is public reads.
- Impersonation only for the real Admin role; the admin section, `/api/members` and `/api/calendar-rules` read-only while it lasts; `x-acting-user` on unsafe requests.
- An account deleted in the Intranet has no access (`accessRevokedAt`), checked on every request and found by the daily re-check even if it never signs in again; only an authenticated Intranet lookup gives it back.
- The Intranet token never travels over `http:` to a public host in production, and logs never carry an email (`accountRef`).
- Activity readers re-check visibility with the current actor and never show others' IPs or emails to non-Admins.
- Email notifications leave through the outbox after commit, are composed with the recipient's visibility, never carry document or amendment text, and never put an address in a log, an audit row or the delivery log.
- An executive office, the person who acted for it and its acronym in an amendment code never reach an account that may not see the offices (`canSeeExecutiveMembers`): the server answers the generic "CEA" everywhere a member leaves it, PDFs included, and never takes the generic id for a member. The only real offices such an account reads are in the amendment composers: the member list (`GET /api/members?for=amendment`, for accounts that present amendments), which says nothing about who presented what, and the real authors of a draft it may edit (`GET .../amendments/[amendment]/authors`, only while the draft can still be edited). Neither carries a person. Speaking turns are the one exception (user's decision of 2026-11-21): a turn names the office by its own acronym, with the person, for everyone (`toTurnDto` in `server/utils/domain/speakers.ts`).

```bash
pnpm verify    # nuxt prepare, then lint, format:check, typecheck, i18n:check, i18n:audit-identical and test side by side (scripts/verify.mjs)
bash ./scripts/deploy.sh    # pnpm verify while it builds the image, push to GHCR once both pass and roll out on the VPS (DEPLOYMENT.md); refuses a dirty tree without --allow-dirty, asks before deploying while an assembly is in session, dumps the database before migrating; --seed also runs the RBAC seed
bash ./scripts/rollback.sh  # previous image; refuses one older than the database's migrations without --force (restore the pre-deploy dump first)
bash ./scripts/clone-prod-db.sh  # replace the local database and uploads with production's (DEPLOYMENT.md); backups/ keeps both sides
```

## Verification Checklist

Run before handing off code changes:

```bash
pnpm lint
pnpm format:check
pnpm typecheck
pnpm i18n:check
pnpm i18n:audit-identical
pnpm test
pnpm build
```

`pnpm verify` runs all of it except `pnpm build`, side by side after one `nuxt prepare` (`scripts/verify.mjs`: Vitest on half the cores, the type check through `vue-tsc -b` on incremental build info in `.nuxt`; `VERIFY_SERIAL=1` runs the steps one at a time), and stamps the tree it passed on (`node_modules/.cache/verify/tree`). `scripts/deploy.sh` runs it while the image builds and pushes nothing unless both pass; it skips it only for `DEPLOY_SKIP_VERIFY=1` or a tree that already passed unchanged (`DEPLOY_REVERIFY=1` runs it again; `DEPLOY_SKIP_BUILD=1` does not skip it). `pnpm lint` and `pnpm format:check` keep content caches in `node_modules/.cache`. Tests that spawn processes one after another go in several files, since Vitest runs files side by side (the DOCX converter's `docx*.test.ts` share `server/testing/docx.ts`, outside what Nitro scans).

Also verify manually when relevant:

- unauthenticated users land on `/login`;
- Google sign-in calls role sync and preserves privileged roles, and an account the Intranet deleted is refused;
- admin pages reject users without `user:manage_roles` or `role:manage_permissions` server-side, only an Admin gives or takes the Admin role, and only an Admin changes Secretaría's and Presidencia's access;
- ES and EN UI both render new strings;
- document content stays block-based and escaped on render;
- amendment incorporation updates document content and history;
- PDF export survives app restart because files are persisted.

## Commit Guidelines

Use Conventional Commits:

```text
feat: add amendment proponent decision workflow
fix: preserve admin role during external role sync
docs: update deployment runbook
refactor: extract localized content helpers
a11y: add diff display preferences
```

Never add a `Co-Authored-By` trailer to a commit, nor a "Generated with" line to a pull request, unless `.claude/settings.json` sets `attribution.commit` (or `attribution.pr`). An agent that writes the change is the tool, not a co-author, even when the harness's default commit template suggests one. Commits are signed (`commit.gpgsign`); never bypass signing.
